What each workload measures

WorkloadTiming boundary and API choices
Load FEN + legal movesParse FEN and construct a game inside every timed iteration, then access its moves. chess-on-go uses NewGameFromFEN and LegalMovesInto with a reusable buffer. corentings uses FEN, NewGame, and ValidMovesUnsafe. Constructor validation and bookkeeping differ; this is an end-to-end API workload, not isolated generator timing.
PerftInitial position, depth 4 (197,281 leaves); Kiwipete, depth 3 (97,862 leaves). chess-on-go uses SearchBoard.Perft; corentings uses Position.Update and the non-copying ValidMovesUnsafe. Both bulk-count depth one and skip PGN and draw history. Root setup and warm-up are excluded.
FEN exportSerialize the already-loaded initial position. Setup is excluded; the returned string is retained.
Cached legal moves, copyCopy an already-computed initial-position move list: LegalMovesInto(nil) versus ValidMoves(). Both allocate defensive slices. This measures copy cost and representation size, not move generation. Both libraries also offer ways to avoid this allocation.
Parse SANDecode Nf3 in the initial position with legal moves already cached. No move is applied. ParseMoveSAN versus AlgebraicNotation.Decode.
Load PGNParse the same unannotated 15-ply main line from scratch. chess-on-go uses LoadPGN; corentings uses PGN and NewGame. Both end at the same FEN, but corentings builds a richer move tree.

The comparison is a separate Go module with a pinned dependency and a local replace for chess-on-go. It adds no runtime dependency to the package. Before timing, tests check identical legal move sets, expected perft counts, unchanged roots, SAN resolution, and the final PGN position.

The cases ran sequentially in one benchmark process, without parallel test or fuzz jobs. Sample order was fixed, not randomized. The report does not cover every position, variant, compiler, architecture, or annotated PGN workload.

Why the numbers differ

  • Traversal favors mutable board state. chess-on-go makes and unmakes moves in place, reuses undo storage, and writes generated moves into local buffers. corentings creates child positions and uses larger move structures. Its non-copying move-list API is used here to avoid penalizing it for unnecessary defensive copies.
  • Zero allocations is a warmed-traversal result. SearchBoard construction and its first undo-storage growth happen before timing. Cold setup still allocates.
  • SAN parsing avoids candidate simulations. chess-on-go filters by destination and matches legal candidates using stack buffers. This benchmark is one simple, non-capturing SAN move; it does not represent all SAN inputs.
  • PGN does different amounts of work. chess-on-go stores a played main line. corentings also supports annotations and variation trees. Compare the functionality your application needs alongside the timing.
  • FEN export is close. The median times are similar despite fewer allocations in chess-on-go. No blanket “faster everywhere” conclusion follows from this report.

Choose the right scope

Both libraries provide standard chess rules and notation. corentings/chess offers a wider toolkit; chess-on-go concentrates on game state, explicit variants, and traversal.

Run it yourself

git clone https://github.com/chesshere-com/chess-on-go.git
cd chess-on-go
# Exact measured engine plus comparison harness:
git checkout 7961deaedc2dc5babf54aedc6d16228c1c3e5646
cd benchmarks/corentings
go test ./...
GOMAXPROCS=1 go test -run '^TestEquivalentWorkloads$' \
  -bench '^BenchmarkCompare$' -benchmem -benchtime=250ms -count=8 .

The source's go.mod pins corentings/chess to v2.6.1 and uses the local checkout for chess-on-go. The pinned checkout above adds only the harness and benchmark documentation to fc6ae9c, preserving the exact measured engine. Use your current checkout instead to measure later changes.

For your own changes, keep the compiler, machine, positions, and timing boundaries constant. Collect repeated samples and use benchstat to evaluate differences instead of comparing single runs.
